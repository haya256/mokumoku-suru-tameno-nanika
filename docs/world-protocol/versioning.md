# バージョンと互換性のルール

## 版の付け方

版は `MAJOR.MINOR`(例: `1.0`, `1.3`, `2.0`)で表します。

| 変更の種類 | 上げる番号 | 例 |
|---|---|---|
| フィールドの追加 | MINOR | 在室者に `status` を追加 |
| 空間種別の追加 | MINOR | `space.type` に `whiteboard` を追加 |
| 列挙値の追加 | MINOR | `state` に `break` を追加 |
| 必須だったものを任意にする | MINOR | |
| フィールドの削除・改名・型の変更 | **MAJOR** | `ts` を ISO 8601 文字列にする |
| 既存フィールドの意味の変更 | **MAJOR** | `pose` の範囲を変える |
| 任意だったものを必須にする | **MAJOR** | |
| URL の構造の変更 | **MAJOR** | |

MINOR の変更は、**古い接続側がそのまま読める**ものだけです。古い接続側が読めなくなる変更は、どんなに小さくても MAJOR です。

## 互換性を支える3つの約束

### 1. 接続側は知らないものを無視する(must-ignore)
接続側は次のものを**エラーにせず無視しなければなりません**。

- 知らないフィールド(どの階層でも)
- 知らない空間種別(`space.type`) → 表示名と、あれば絵だけを出す(各版の spec に表示方法を定める)
- 知らない列挙値(例: 知らない `state`) → 各版の spec が定める既定値として扱う
- 自分より新しい MINOR 版(例: 1.0 の接続側が `"version": "1.4"` を受け取る) → 1.0 として読む

この約束があるので、提供側は接続側を待たずに MINOR 版を上げられます。

### 2. 提供側は MAJOR 内で既存のフィールドを壊さない
同じ MAJOR のあいだ、提供側は既存のフィールドの名前・型・意味を変えてはいけません。
新しいことは常に「足す」ことで表現します。

### 3. 提供側は複数の MAJOR を同時に提供してよい
MAJOR を上げるときは、しばらく旧 MAJOR のスナップショットも並べて提供すべきです。
Discovery 文書の `versions` に両方を載せ、接続側は**自分が読める最大の MAJOR**を選びます。

```json
"versions": [
  { "version": "1.6", "snapshot": "/world-api/v1/snapshot" },
  { "version": "2.0", "snapshot": "/world-api/v2/snapshot" }
]
```

旧 MAJOR の提供をやめるときは、[`CHANGELOG.md`](CHANGELOG.md) で事前に予告します。

## 版の選び方(接続側)

1. `GET /.well-known/mokumoco-world` を取る
2. `protocol` が `"mokumoco-world"` でなければ、この仕様の相手ではない
3. `versions` のうち、MAJOR が自分の対応範囲にあるものの中で MAJOR が最大のものを選ぶ
4. 選べなければ「対応していない相手」として扱う(接続しない、または [`legacy.md`](legacy.md) の方式を試す)

Discovery は登録時に1回取れば十分ですが、提供側が更新されることもあるので、時々(例: 1時間ごと、または取得失敗が続いたとき)取り直すべきです。

## 仕様書の版と実装の版

- 仕様書の版は `docs/world-protocol/CHANGELOG.md` で管理します
- 実装(ソフトウェア)のバージョンとは独立です。Discovery の `software` 欄は情報提供のためだけのもので、接続側はこれで動作を変えるべきではありません
