## 1. 用語と前提

| 用語 | 意味 |
|---|---|
| 提供側 | 自分の空間を公開するサーバー |
| 接続側 | 提供側を巡回し、その内容を自分の参加者に見せるサーバー |
| ルートURL | 接続側の管理者が登録する提供側のURL。`https://example.com` のようにスキームとホスト(とポート)だけで、パスを持たない |
| 空間 | 提供側が公開する「場所」。もくもく会の9部屋の建物、動画配信など。種類を `space.type` で表す |
| 在室者 | 空間の中にいる人やNPC |
| スナップショット | ある時点の空間とチャットの全状態を1つにまとめたJSON |

- 通信は HTTP(S) の `GET` だけです。提供側への書き込みはこの仕様の範囲外です
- JSON は UTF-8、`Content-Type: application/json` で返さなければなりません
- 提供側は認証なしの `GET` で応答しなければなりません(公開を前提とした情報だけを載せる。[README](../README.md#公開性について) 参照)
- 時刻は特に断りがない限り **UNIX時刻(秒、小数可)** の数値です
- 応答が HTTP 200 以外なら、接続側はその回の取得を失敗として扱います

## 2. Discovery

提供側は次のURLで Discovery 文書を返さなければなりません。

```
GET <ルートURL>/.well-known/mokumoco-world
```

```json
{
  "protocol": "mokumoco-world",
  "name": "夜のもくもく会",
  "versions": [
    { "version": "1.0", "snapshot": "/world-api/v1/snapshot" }
  ],
  "minPollIntervalSec": 5,
  "software": { "name": "mokumoku-suru-tameno-nanika", "url": "https://github.com/..." }
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `protocol` | 文字列 | ○ | 常に `"mokumoco-world"` |
| `name` | 文字列 | ○ | 空間の表示名(接続側の管理者が名前を入れなかったときの既定値) |
| `versions` | 配列 | ○ | 提供している版。1つ以上。MAJOR ごとに1つ |
| `versions[].version` | 文字列 | ○ | `"MAJOR.MINOR"`。その MAJOR で提供している最新の MINOR |
| `versions[].snapshot` | 文字列 | ○ | その版のスナップショットのURL。相対URLならDiscovery文書のURLを基準に解決する(§6.1) |
| `minPollIntervalSec` | 数値 | | 巡回の最短間隔(秒)の希望。省略時は 5 |
| `software` | オブジェクト | | 実装の名前・URLなど。情報提供のみ。接続側はこれで動作を変えるべきではない |

- スナップショットのURLは、ルートURLと**同じオリジン**(スキーム・ホスト・ポート)でなければなりません。接続側は違うオリジンを指していたら接続を拒否しなければなりません

## 3. スナップショット

```
GET <versions[].snapshot で示されたURL>
```

```json
{
  "protocol": "mokumoco-world",
  "version": "1.0",
  "generatedAt": 1760000000.25,
  "space": { "type": "room9", "...": "空間種別ごとの中身(§4)" },
  "messages": [ "...チャット(§5)" ]
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `protocol` | 文字列 | ○ | 常に `"mokumoco-world"` |
| `version` | 文字列 | ○ | この応答の版 `"1.MINOR"` |
| `generatedAt` | 数値 | ○ | 応答を作った時刻 |
| `space` | オブジェクト | ○ | 空間(§4) |
| `messages` | 配列 | ○ | チャット(§5)。チャットの無い空間では空配列 |

- スナップショットは**毎回すべての状態を含めます**(差分ではない)。接続側は前回の内容を今回の内容で丸ごと置き換えます
- スナップショット全体の大きさは **1,000,000 バイト以下**にしなければなりません。接続側はこれを超える応答を失敗として扱ってよいです
- スナップショットの中に画像のバイト列を埋め込んではいけません。画像はURLで示します(§6)

## 4. 空間種別

`space.type` で空間の種類を表し、種類ごとに中身が決まります。すべての種別に共通するフィールドは次のとおりです。

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `type` | 文字列 | ○ | 空間種別 |
| `title` | 文字列 | ○ | 空間の題名(画面上部に出す名前。40文字程度まで) |
| `image` | 画像参照 \| null | | マップのマスに出す絵(§6.2)。無ければ null または省略 |

### 4.1 知らない空間種別

接続側は、知らない `type` を受け取ったら**エラーにせず**、`title` と(あれば)`image` だけでマスを表示しなければなりません。
これにより、新しい種別を作った提供側は、古い接続側にも「何かある」ことだけは伝えられます。

### 4.2 `room9` — もくもく会の部屋

9つの部屋がある建物。もくもく会チャットが提供する空間です。

```json
{
  "type": "room9",
  "title": "夜のもくもく会",
  "favicon": "🏠",
  "state": "normal",
  "closingAt": 1760010000,
  "image": { "url": "/room-image.webp", "version": "3", "mime": "image/webp" },
  "occupants": [
    {
      "id": "c-8f3a",
      "name": "たろう",
      "task": "読書",
      "start": "19:30",
      "end": "21:00",
      "cell": 4,
      "pose": 1,
      "avatar": { "url": "/chara-custom/c-8f3a.png", "version": "12", "mime": "image/png" },
      "npc": null
    }
  ]
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `favicon` | 文字列 | | 空間を表す絵文字1つ |
| `state` | 文字列 | | `"normal"` / `"preparing"`(準備中) / `"closed"`(閉店)。省略時と**知らない値は `"normal"`** として扱う |
| `closingAt` | 数値 \| null | | 閉店予定時刻。未定なら null または省略 |
| `image` | 画像参照 \| null | | 建物の絵。正方形を推奨。9部屋の位置は絵の3×3等分 |
| `occupants` | 配列 | ○ | 在室者。0〜9件 |

在室者(`occupants[]`):

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `id` | 文字列 | ○ | 在室中に変わらない識別子。空間内で一意。64文字以下 |
| `name` | 文字列 | ○ | 表示名 |
| `task` | 文字列 | | もくもくする内容 |
| `start` | 文字列 | | 開始時刻の表示用文字列(例 `"19:30"`)。提供側の現地時刻。解釈せずそのまま表示する |
| `end` | 文字列 | | 終了予定の表示用文字列。未定なら空文字 |
| `cell` | 整数 | ○ | いる部屋の番号 1〜9(左上から右へ、上の段から順)。在室者どうしで重複しない |
| `pose` | 整数 | | キャラのポーズ 0〜2。範囲外・省略は 0 として扱う |
| `avatar` | 画像参照 \| null | | キャラの絵。null なら接続側の既定のキャラ絵を使う |
| `npc` | NPC情報 \| null | | 人ではなくNPCならその情報。人なら null または省略 |

NPC情報(`npc`):

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `kind` | 文字列 | ○ | NPCの種類 |
| `props` | オブジェクト | | 種類ごとの値 |

v1.0 で定めるNPCの種類:

| `kind` | `props` | 見た目 |
|---|---|---|
| `basic` | なし | 普通のキャラ(喋らない置物) |
| `clock` | なし | 時計。閲覧者の端末の時刻を出す |
| `calendar` | なし | カレンダー。閲覧者の端末の日付を出す |
| `youtube` | `videoId`: YouTube の動画ID(英数字と `_` `-` の11文字) | YouTube動画を再生できるテレビ |

接続側は、知らない `kind`、対応していない種類、`props` が不正なNPCを `basic` として表示しなければなりません。

### 4.3 `stream` — 動画・音声の配信(v1.0 で予約)

ライブ配信などの動画・音声を流す空間です。v1.0 では**形だけを定め**、接続側が再生に対応することは必須にしません。
対応していない接続側は §4.1 のとおり `title` と `image` だけを出します。

```json
{
  "type": "stream",
  "title": "作業BGM配信",
  "image": { "url": "/thumbnail.jpg", "version": "1", "mime": "image/jpeg" },
  "live": true,
  "media": [
    { "kind": "video", "format": "hls", "url": "https://cdn.example.com/live/index.m3u8" },
    { "kind": "audio", "format": "hls", "url": "https://cdn.example.com/live/audio.m3u8" }
  ]
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `live` | 真偽値 | | 今配信中か。false なら接続側は「配信していません」と出してよい |
| `media` | 配列 | ○ | 再生できる形式の候補。接続側は**自分が再生できる最初の候補**を選ぶ |
| `media[].kind` | 文字列 | ○ | `"video"`(映像+音声) / `"audio"`(音声のみ) |
| `media[].format` | 文字列 | ○ | `"hls"`(HTTP Live Streaming) / `"mp4"`(通常の動画ファイル)。知らない値の候補は飛ばす |
| `media[].url` | 文字列 | ○ | **参加者のブラウザが直接読み込むURL**(§6.3) |

- 接続側は、参加者が操作するまで再生を始めるべきではありません(自動再生しない)

## 5. チャット

`messages` は古い順に並べます。

```json
{
  "id": "m-x81k",
  "ts": 1760000123.5,
  "author": { "name": "たろう", "uid": "c-8f3a" },
  "text": "こんばんは",
  "image": { "url": "/message-image/Qw3r.webp", "mime": "image/webp" },
  "system": false
}
```

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `id` | 文字列 | ○ | 発言の識別子。スナップショットをまたいで変わらない。空間内で一意 |
| `ts` | 数値 | ○ | 発言時刻。**接続側は自分のチャットと相手のチャットをこの値で1本の時系列に並べる** |
| `author` | オブジェクト \| null | | 発言者。システムからのお知らせは null |
| `author.name` | 文字列 | ○ | 発言時の表示名 |
| `author.uid` | 文字列 \| null | | 発言者が在室者なら、その `occupants[].id`。吹き出しをキャラの頭上に出すのに使う |
| `text` | 文字列 | ○ | 本文(プレーンテキスト。改行可。HTMLではない) |
| `image` | 画像参照 \| null | | 添付画像 |
| `system` | 真偽値 | | 入退室などのお知らせなら true |

- 表示用の「何時何分」は、接続側が `ts` から自分の参加者向けに作ります
- 提供側は、新しいものから **200件まで**を入れるべきです(全件を返す必要はない)。接続側は、スナップショットに無い古い発言を「消えた」と扱ってよいです
- 提供側で発言が削除されたときは、スナップショットから消すだけで構いません。接続側は次の巡回でそれを表示から外すべきです

## 6. メディアの扱い

### 6.1 URLの解決
スナップショット内のURLが相対URLなら、**そのURLが書かれていた文書のURL**(Discovery ならDiscovery文書のURL、スナップショットならスナップショットのURL)を基準に、RFC 3986 に従って解決します。

### 6.2 画像(中継するメディア)
部屋の絵・キャラの絵・チャットの画像などは、**接続側サーバーが取ってきて自分の参加者に中継します**。参加者のブラウザが提供側に直接アクセスしないことで、提供側にCORS設定が要らず、参加者の人数に関係なく提供側の負荷が一定になり、参加者のIPアドレスが提供側に渡りません。

画像参照の形:

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `url` | 文字列 | ○ | 画像のURL。解決後にルートURLと**同じオリジン**でなければならない |
| `version` | 文字列 | | 中身の版。中身が変わったら必ず別の値にする。同じ値のあいだは取り直さなくてよい |
| `mime` | 文字列 | | `image/png` / `image/webp` / `image/jpeg` のいずれか |

- 形式は PNG・WebP・JPEG のいずれか。1枚 **6,000,000 バイト以下**
- 接続側は、ルートURLと違うオリジンの画像を中継してはいけません(提供側のスナップショットを踏み台に、接続側サーバーから任意のURLへアクセスさせないため)
- 接続側は、`version` が同じあいだはキャッシュを使ってよいです。ただし提供側の再起動で値が巻き戻ることに備え、一定時間(例: 5分)ごとに取り直すべきです
- チャット画像のように中身が変わらないものは、`version` を省略してよいです(URLが変われば別の画像)

### 6.3 動画・音声ストリーム(直接参照するメディア)
`stream` 空間の `media[].url` は、**参加者のブラウザが直接読み込みます**。中継すると接続側サーバーの帯域と負荷が大きくなりすぎるためです。

- このURLは提供側と違うオリジン(配信用CDNなど)でもよい
- 提供側(配信元)は、ブラウザから読めるよう必要なCORSヘッダーを付けなければなりません
- **参加者が再生すると、参加者のIPアドレスが配信元に渡ります**。接続側は、再生ボタンなど参加者の操作があって初めて読み込みを始めなければなりません
- スキームは `https` でなければなりません(参加者の画面が https のとき混在コンテンツで再生できなくなるため)

## 7. 巡回の作法

- 接続側は、Discovery の `minPollIntervalSec`(省略時5秒)より短い間隔でスナップショットを取ってはいけません
- 1回の巡回でスナップショットは1回だけ取ります。画像は `version` が変わったときなど、必要なときだけ取ります
- タイムアウトは5秒程度にすべきです。応答しない提供側が他の提供側の巡回を遅らせないよう、提供側ごとに並行して取るべきです
- 接続側は `User-Agent` に自分の実装名を入れるべきです
- 取得に失敗したら、接続側は**前回の内容を残したまま**「接続できません」などの表示に切り替えるべきです(一瞬の通信断で相手の部屋から人が消えたように見えないように)
- 提供側は `Cache-Control` を付けてよいですが、スナップショットには長いキャッシュを付けるべきではありません

## 8. 安全のための約束

接続側は、提供側から来たものを信用しすぎてはいけません。

- テキスト(名前・作業内容・チャット・題名など)は、HTMLとして解釈せず、エスケープして表示しなければなりません
- 画像は、中継する前に中身の先頭(マジックバイト)を確かめ、PNG・WebP・JPEG のどれかでなければ捨てなければなりません。`mime` やHTTPヘッダーの申告だけを信用してはいけません
- URLのスキームは `http` / `https` だけを受け付けなければなりません(`stream` の `media[].url` は `https` のみ)
- 数値の範囲(`cell`, `pose` など)は受け取った側で範囲に丸めるか、範囲外の項目を捨てなければなりません
- 大きさの上限(スナップショット 1,000,000 バイト、画像 6,000,000 バイト)を超えた応答は、全部読まずに打ち切るべきです
- NPCの `youtube` の `videoId` のように、閲覧者の画面に埋め込むものは、接続側の方針で表示しないことを選んでよいです

## 9. 適合要件のまとめ

### 提供側 v1 準拠
1. `/.well-known/mokumoco-world` で §2 の Discovery 文書を返す
2. `versions` に `"1.x"` を含め、そのURLで §3 のスナップショットを返す
3. スナップショットのURLと画像URLは、ルートURLと同じオリジンにある
4. `space` は §4 のいずれかの種別、または独自の種別(§4.1 で古い接続側にも名前は出る)
5. `messages[].id` と `ts` を必ず付ける
6. 画像は PNG/WebP/JPEG で 6,000,000 バイト以下。中身が変わったら `version` を変える
7. 認証なしで取れる
8. `schemas/snapshot.schema.json` と `schemas/discovery.schema.json` に合格する

### 接続側 v1 準拠
1. Discovery で版を選び、`minPollIntervalSec` を守って巡回する
2. 知らないフィールド・空間種別・列挙値・NPCの種類を、エラーにせず §4・`versioning.md` のとおりに扱う
3. 同じ MAJOR の新しい MINOR 版を、知っている部分だけで読む
4. チャットを `ts` で自分のチャットと1本の時系列に並べる
5. 画像はルートURLと同じオリジンのものだけを中継し、マジックバイトを確かめる
6. テキストをエスケープして表示する
7. 取得失敗時は前回の内容を残してオフライン表示にする

## 10. 付録: もくもく会チャットでの対応

この仕様の最初の実装であるもくもく会チャットでは、次のように対応しています(参考情報。仕様の一部ではありません)。

| 仕様 | もくもく会チャット |
|---|---|
| Discovery | `GET /.well-known/mokumoco-world` |
| スナップショット | `GET /world-api/v1/snapshot` |
| `room9.image` | `/room-image.webp`(`version` は部屋画像を変えるたびに増える番号) |
| `occupants[].avatar` | `/chara-custom/<id>.png`(カスタム画像が無い人は null) |
| `messages[].image` | `/message-image/<id>.webp` |
| `messages` の件数 | 新しいものから200件 |
| 旧来の接続方式 | `/board` `/messages` `/status` も引き続き提供([`../legacy.md`](../legacy.md)) |
